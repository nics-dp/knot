## 0. 文件用途與閱讀方式

本文件是開發的唯一依據，供 Claude Code 在本機接手開發。原為 Claude Docs 文件，匯出後以 repo 的 `docs/SPEC.md` 為正本，之後的修改都在這裡進行。

- **本規格為準。** 與其他資料衝突時，以本規格為準；需要改規格時，先提出再動手。
- **背景資料：** `docs/ideas.md` 收錄設計緣由與尚未納入規格的構想，不是需求清單。
- **設計稿是視覺參考。** 版面、配色、互動以第 6 節描述為準，設計稿用來對照外觀。
- **標為「待定」的項目不要自行決定。** 實作到該處時先停下，列出選項請使用者決定。
- **用語：** 「卡片」指卡片樹上的節點；「本文」指 agent 撰寫或人工撰寫的段落文字；「素材」指匯入並確認過的來源區塊；「意圖」指為卡片寫下的要點與說明，是 agent 撰寫本文時的提示詞（見 5.4）；「agent」指使用者在本機執行、透過 MCP 操作 Knot 的 AI 助理（初期為 Claude Code）；「留言」與「待辦」指卡片上的指示（見 5.11）。

- **有疑問時：** 把問題記在 `docs/QUESTIONS.md`，每題寫明相關章節、問題、可能的選項與各自影響。使用者會帶回本規格討論，定案後更新本文件，再從 `QUESTIONS.md` 移除該題。

## 1. 產品概要與範圍

Knot 是一個單機、單人使用的報告撰寫工具，也是 agent 撰寫報告時的白板：

- **agent 負責需要判斷的事。** 使用者讓 agent 讀取報告目錄中的資料，agent 依 Knot 提供的 skill 學會如何建立素材與卡片、規劃整份報告的結構、為每張卡片寫下意圖，並與使用者討論調整；最後逐段向 Knot 取得撰寫所需的內容，寫好本文交回。
- **Knot 負責需要保證的事。** 素材逐字出自原文；事實只存一份、引用與交互參照必須存在；結構合法；每次修改都記成修改組，可以檢視、比較與復原；LaTeX 匯出結果固定。這些檢查做在 Knot 內，不依賴 agent 自律。
- **使用者在 Knot 檢視與調整。** 卡片樹、全文與編輯區讓使用者看到 agent 的成果、直接修改，並以卡片上的留言與待辦把意見交代給 agent（5.11）。
- **Knot 本身不呼叫 LLM API。** 生成、相關段落的連動修改、文風萃取等需要模型的工作都交給 agent；Knot 不保存金鑰、不選擇模型。
- **沒有 agent 也能使用。** 建立與編輯卡片、匯入素材（anydoc 或手寫 Markdown）、撰寫本文、檢查與匯出都能單獨在 Knot 完成；需要 agent 的工作在畫面上以待辦的形式留給 agent。

最後單向匯出成 LaTeX 專案，交給使用者在自己的 LaTeX 環境完成。

初期對象是廠商撰寫政府專案的結案技術報告與案例報告，但資料模型與流程不得寫死政府報告的格式。

**資料外送：** agent 讀到的素材與卡片會送到 agent 所用的模型服務，Knot 無法把關。哪些資料可以交給 agent 處理由使用者判斷；不經 agent 的匯入與撰寫方式一直保留。

**範圍內**

- 報告建立（從範本或空白開始）
- 素材庫（獨立頁面）：匯入、切分成段落與表格區塊、逐字比對、確認、全文搜尋
- 事實表與實體表，可綁定到表格儲存格
- 卡片樹：最多四層標題（例如 3.1.1.1），加上段落、表格與圖，拖曳重組，選取置中
- 段落撰寫與編輯、段落關係、狀態管理；agent 交回的本文在 Knot 驗證
- 相關段落的連動：依賴分析、為受影響的段落產生待辦（由 agent 處理並直接寫入）
- 文風設定：規則的編輯、分層繼承、報告內快照
- 交接檢查：一致性、契約項目涵蓋、缺少依據的陳述
- LaTeX 專案匯出，含局部匯出
- agent 介面：MCP 端點、隨 Knot 發佈的 skill（5.12）
- 卡片上的留言與待辦（5.11）
- 畫面同步：agent 在背景寫入時即時更新畫面、衝突檢查（5.13）

**範圍外（不要實作）**

- 多使用者、權限、雲端同步
- 從 LaTeX 把修改讀回工具
- 審查意見回覆流程、期中到期末的延續
- Word 匯出
- Embedding 與向量搜尋：素材檢索只用 Datalevin 全文搜尋
- Knot 直接呼叫 LLM API（金鑰、模型選擇、prompt 範本）：需要模型的工作交給 agent
- 在 Knot 內執行或排程 agent：agent 由使用者在自己的環境啟動
- 工具內編譯 LaTeX：輸出正確性由使用者自行編譯驗證

## 2. 技術架構

應用程式是本機 Web 應用：Clojure 後端在 localhost 提供 API 與靜態檔，前端以 ClojureScript 撰寫，在使用者的瀏覽器中執行。前後端共用 `.cljc` 程式碼（例如編號規則、label 產生、資料驗證）。

**後端**

- Clojure（deps.edn）、http-kit（伺服器，含 Server-Sent Events）、reitit、muuntaja（前後端以 EDN 交換，`application/edn`）、malli（資料驗證）
- integrant 管理元件生命週期，搭配 integrant.repl
- Datalevin：嵌入式資料庫；全文搜尋用於素材檢索；不使用向量與 embedding 功能
- 檔案解析交給外部工具 anydoc 轉成 Markdown（見 5.2）；後端以 commonmark-java 加 GFM 表格擴充解析 Markdown
- MCP 端點的 JSON 以 muuntaja 已帶入的 jsonista 處理，預期不新增相依套件

**前端**

- shadow-cljs、Replicant 負責渲染、Nexus 負責 action 分派
- 本文編輯器用 Tiptap 的核心套件 @tiptap/core（ProseMirror，不依賴 React），在 Replicant 的掛載生命週期中建立，以自訂 inline node 呈現事實引用與 LaTeX 交互參照
- 拖曳用瀏覽器原生 HTML5 drag and drop，另提供鍵盤上移、下移作為替代
- 字型優先使用系統字型（PingFang TC、Microsoft JhengHei、Noto Sans TC），不依賴網路字型，因為使用環境可能離線

選用 Replicant 與 Nexus 的理由：畫面是狀態的純函式，事件處理以資料描述，view 函式可以寫成 `.cljc`，在 JVM 上直接測試輸出的 hiccup。這是偏好而非硬性要求；遇到 Replicant 難以處理的需求時，可改用 Reagent 搭配 re-frame，但要先提出。

**agent 介面**（詳見 5.12）

- Knot 不呼叫 LLM。需要模型的工作（規劃結構、整理素材、撰寫本文、連動修改相關段落、萃取文風）由 agent 完成，透過 MCP 讀寫 Knot。
- 後端提供 `/mcp` 端點，使用 MCP 的 Streamable HTTP 傳輸（JSON-RPC：`initialize`、`tools/list`、`tools/call`）；工具直接呼叫 `knot.db`、`knot.tree`、`knot.context`，與畫面共用同一個資料庫連線與驗證。
- 只綁 localhost，並檢查 `Origin` 標頭，防止網頁透過 DNS rebinding 呼叫本機服務。
- Claude Code 的設定：`claude mcp add --transport http knot http://localhost:3000/mcp`。
- skill 放在 repo 的 `skills/`，與 MCP 工具一起管理版本、隨 Knot 發佈。

**HTTP API**（皆在 `/api` 底下，請求與回應為 EDN）

| 方法與路徑 | 用途 |
|---|---|
| `GET /api/report` | 讀取整份報告（報告資訊、卡片、關係、素材區塊、事實） |
| `POST /api/report/changes` | 寫入一個修改組（`knot.sync/diff` 的格式，以 malli 驗證） |
| `POST /api/report/undo` | 復原最近一個修改組（屬於一組時整組復原），回傳復原後的報告 |
| `POST /api/report/info` | 修改報告名稱與副標（不屬於修改組） |
| `GET /api/report/nodes/:id/previous` | 卡片本文的前一版（5.4） |
| `GET /api/report/nodes/:id/history` | 卡片的修改紀錄（5.4 卡片歷程） |
| `GET /api/report/nodes/:id/changes/:changeset-id` | 某次修改前後的本文（5.4 卡片歷程） |
| `GET /api/events` | Server-Sent Events：任何修改組寫入後通知畫面（5.13） |
| `POST /mcp` | MCP 端點（5.12），不在 `/api` 底下 |
| `POST /api/dev/sample` | 開發用：把範例報告匯入空白報告 |

**報告目錄**

一個報告目錄就是一份報告，只有一個資料庫。啟動時讀取目錄中的報告；目錄中還沒有報告時，建立一份空白報告（名稱取自目錄名稱）。

```text
<報告目錄>/                    啟動時所在的目錄，或命令列參數指定
├─ .knot/db/                   Datalevin：這份報告的所有資料
├─ sources/                    匯入的原始檔複本
├─ figures/                    使用者提供的圖檔
└─ export/                     預設的 LaTeX 匯出位置
```

**Repo 結構**

```text
deps.edn  shadow-cljs.edn  package.json  bb.edn  CLAUDE.md
src/clj/knot/                  後端：db、api、server、system、seed、ingest（之後：mcp、events、export、checks）
src/cljc/knot/                 共用：tree（樹運算、編號、合法性、關係）、order-key、layout、
                               ui（狀態轉換）、context（生成時的參考內容）、sync、diff、views
src/cljs/knot/                 前端：app（渲染迴圈、actions、同步）、prose-editor（Tiptap）
skills/                        隨 Knot 發佈的 agent skill（規劃、匯入、撰寫，見 5.12）
resources/public/              index.html、css、編譯後的 js
dev/user.clj                   REPL 進入點
test/                          clj 與 cljs 測試
test-resources/fixtures/       虛構的範例報告、素材、agent 交回的本文
docs/SPEC.md  docs/ideas.md  docs/design/  docs/QUESTIONS.md
```

啟動方式：在報告目錄執行 `java -jar knot.jar`（或 `java -jar knot.jar <報告目錄>`），啟動伺服器並開啟瀏覽器；開發時為 `clojure -M:run [報告目錄]`，REPL 開發使用 `local/report`。jar 的打包方式待 M8 前後處理。

## 3. 開發環境

開發採 REPL 優先：後端與前端各開一個 nREPL，Claude Code 透過命令列工具對它們求值，先在 REPL 驗證行為，再寫成測試。

**兩個 nREPL**

| 用途 | 啟動指令 | Port |
|---|---|---|
| Clojure 後端 | `clojure -M:dev:nrepl` | 7888 |
| ClojureScript 前端 | `npx shadow-cljs watch app` | 7889（設定在 shadow-cljs.edn） |

- `:nrepl` alias 包含 nrepl 與 cider-nrepl，啟動後寫出 `.nrepl-port`。
- 前端 REPL：連上 7889 後執行 `(shadow.cljs.devtools.api/repl :app)`，瀏覽器需開著頁面。
- 用 babashka 的 `bb.edn` 包裝常用指令：`bb dev`、`bb test`、`bb cljs-test`、`bb lint`。
- 原則上由使用者啟動這兩個 nREPL。Claude Code 發現沒在執行時，可以在背景啟動，但不要關閉使用者已啟動的行程。

**`dev/user.clj` 提供的函式**

- `(go)`、`(halt)`、`(reset)`：透過 integrant.repl 啟動、停止、重新載入系統
- `(seed!)`：把虛構範例匯入目前的空白報告；`(seed! "path")` 匯入指定的報告 EDN（例如本機測試報告）
- `(wipe!)`：刪除開發用報告目錄（`local/report`）的資料庫並重新啟動，得到空白報告
- `(db)`：取得目前報告的 Datalevin 連線，方便直接下查詢
- `(import-file! "path")`：對單一檔案執行外部轉換與匯入，方便檢查轉換結果（M5 加入）
- `(mcp! "tool" {...})`：直接呼叫一個 MCP 工具並回傳結果，方便在 REPL 驗證工具行為（M3 加入）

**Claude Code 用的工具**

安裝 clojure-mcp-light（需要 babashka 與 bbin），它提供兩個工具：

- `clj-nrepl-eval`：從命令列對 nREPL 求值，例如 `clj-nrepl-eval -p 7888 "(user/reset)"`
- `clj-paren-repair-claude-hook`：在 Claude Code 寫入或編輯 `.clj` 檔時自動修正括號，設定在 `.claude/settings.json` 的 hooks

安裝時用 git tag 固定版本，並把版本記在 `CLAUDE.md`。

**每項工作的完成條件**

1. 修改後在 REPL 重新載入並驗證行為。
1. 補上或更新測試：後端 `clojure -M:test`，前端 `bb cljs-test`。
1. 測試全數通過，shadow-cljs 編譯沒有 warning，clj-kondo 沒有 error。

**`CLAUDE.md` 要寫的內容**

M0 時建立，至少包含：兩個 nREPL 的 port 與啟動方式、`clj-nrepl-eval` 用法、`dev/user.clj` 的函式、測試與 lint 指令、第 8 節的開發守則，以及「先讀 docs/SPEC.md」。

## 4. 資料模型

每個報告目錄一個 Datalevin 資料庫，不另設跨報告共用的資料庫。下列 schema 是 M1 的起點，實作時可補充屬性，但改名或刪除要先更新本節。

**報告資料庫**

```clojure
;; 共通：每個實體都有 :<ns>/id（:db.type/uuid、:db.unique/identity）
;; 結構化值（欄位定義、規則、快照）以 pr-str 存成字串，讀取時用 malli 驗證

;; 報告
:report/id              uuid
:report/title           string
:report/subtitle        string   ; 顯示用副標題
:report/style-name      string   ; 顯示用文風名稱
:report/style-snapshot  string   ; 套用時複製的文風規則（EDN）
:report/style-source    uuid     ; 來源文風設定，只用於追溯與提示同步

;; 卡片（標題、段落、表格、圖）
:node/kind        keyword  ; :heading :intro :paragraph :table :figure
:node/parent      ref      ; 第一層標題沒有 parent
:node/order-key   string   ; 分數索引，同一 parent 內排序
:node/name        string   ; 標題名稱，不含編號；層級由樹的深度決定（1–4），不另存
:node/title       string   ; 段落、表格、圖的標題
:node/draft       string   ; 意圖：使用者或 agent 寫下的要點與說明，作為撰寫本文的提示詞；fulltext
:node/prose       string   ; 本文，ProseMirror JSON
:node/status      keyword  ; :none :ai :human（:ai 表示 agent 撰寫）
:node/version     long     ; 每次內容變更 +1
:node/target-chars long    ; 選填：目標字數（篇幅），標題為整章／整節的目標
:node/label       string   ; LaTeX label，:db.unique/value
:node/facts       ref many ; 由 prose 抽出的事實引用
:node/rows        ref many ; 由 prose 抽出的實體引用
:node/table       ref      ; 表格卡片引用的素材表
:node/table-view  string   ; 欄位、篩選、排序（EDN）
:node/table-content string ; 表格卡片自己的內容 {:columns [欄名] :rows [[儲存格]]}（EDN），由 agent 以 write_table 寫入（M6；素材表接上後兩種來源並存）
:node/figure-file string   ; 圖檔相對路徑
:node/caption     string
:node/contract-items ref many

;; 段落關係
:relation/key     string   ; :db.unique/identity，見 tree/relation-key（相鄰：每對一條；不相鄰：每對每種類型一條）
:relation/from    ref
:relation/to      ref
:relation/type    keyword  ; 相鄰：:progression :causal :contrast :example
                           ; 不相鄰：:summarizes :basis :echo :contrast
:relation/remote  boolean  ; true 表示不相鄰（任意距離）的關係；:summarizes 一律視為不相鄰
:relation/pending boolean  ; true 表示「待確認」（只用於相鄰關係）

;; 素材
:source/file-name string
:source/path      string   ; 相對於報告目錄
:source/kind      keyword  ; :pdf :docx :xlsx :md :txt
:block/source     ref
:block/kind       keyword  ; :para :table
:block/title      string
:block/text       string   ; fulltext
:block/location   string   ; 例如 "p.12"、"工作表 2"
:block/status     keyword  ; :candidate :confirmed :discarded
:block/verbatim   keyword  ; 逐字比對結果 :match :mismatch，未比對時沒有（5.2；取代原 :block/ai-split）
:block/table      ref      ; 表格區塊對應的表

;; 表格與事實
:table/name       string
:table/kind       keyword  ; :data :entity
:table/columns    string   ; [{:col/id :col/name :col/type}]（EDN）
:table/name-column string  ; 實體表用來當名稱的欄位 id
:row/table        ref
:row/order-key    string
:row/cells        string   ; {col-id value}（EDN）
:fact/key         string   ; :db.unique/identity，例如 "saving-rate.site-a"
:fact/label       string
:fact/value       string   ; 未綁定儲存格時使用
:fact/unit        string
:fact/row         ref      ; 綁定儲存格時：列
:fact/column      string   ; 綁定儲存格時：欄位 id
:fact/block       ref      ; 事實所屬的素材區塊

;; 引用與契約
:citation/node    ref
:citation/block   ref
:citation/row     ref      ; 選填，引用到表格的某一列
:citation/where   string   ; 選填，引用的範圍說明（例如「欄：場域、節電率」）
:citation/order   long     ; 依據在段落中的順序
:contract/code    string   ; 例如 "2.3"
:contract/text    string

;; 卡片上的留言與待辦（5.11）
:note/id          uuid
:note/node        uuid     ; 所屬卡片的 :node/id；沒有時是整份報告的留言（存 id 而非 ref：卡片刪除後復原是新實體）
:note/author      keyword  ; :user :agent :knot（:knot 是 Knot 為相關段落自動產生的待辦，5.6）
:note/text        string
:note/todo        boolean  ; true 表示交代 agent 處理的待辦
:note/state       keyword  ; 待辦才有：:open :done
:note/reply-to    uuid     ; 回覆的留言的 :note/id
:note/at          instant
:note/done-at     instant
:note/changeset   uuid     ; 選填：完成待辦時所做的修改組的 :changeset/id
:note/trigger     uuid     ; :knot 待辦才有：觸發的卡片的 :node/id
:note/dependency  keyword  ; :knot 待辦才有：:summary :argument

;; 修訂、修改組
:changeset/id     uuid
:changeset/origin keyword  ; :manual :propagation :regenerate :move :import :undo
:changeset/by     keyword  ; :user :agent（沒有時為 :user）
:changeset/at     instant
:changeset/label  string   ; 顯示用名稱，例如「移動「異常狀況說明」」；agent 的修改組用工具的 summary 參數
:changeset/undoes ref      ; :undo 修改組所復原的修改組
:changeset/group  string   ; 選填：agent 一次工作的組名（MCP 寫入工具的 group 參數）
:changeset/group-id uuid   ; 同一組的修改組共用；歷程顯示為一筆、復原時整組復原
:changeset/undoes-group uuid ; 整組復原時記下被復原的 group-id
:revision/changeset ref
:revision/collection keyword ; :nodes :relations :blocks :facts
:revision/target  string   ; 「集合/識別鍵」，例如 "nodes/<uuid>"
:revision/node    ref      ; 卡片的修訂才有
:revision/version long
:revision/before  string   ; 變更前快照（前端實體形式的 EDN；新增時沒有）
:revision/after   string   ; 變更後快照（刪除時為 nil）
```

**文風與範本**（5.1、5.7 實作時加入報告資料庫，作為套用時的快照；共用的來源見 5.7）

```clojure
:style/name     string
:style/scope    keyword  ; :org :agency :project
:style/parent   ref
:style/rules    string   ; [{:rule/id :rule/kind :rule/text :rule/example}]（EDN）
:template/name  string
:template/skeleton string ; 章節樹與契約項目（EDN）
```

**資料規則**

- **對外只用 UUID。** Datalevin 的 entity id 不離開 db 命名空間，API 與前端一律用 `:x/id`。
- **編號不儲存。** 章節編號由 `.cljc` 的 numbering 函式依樹的位置計算，前後端共用。
- **排序用分數索引。** 拖曳只改被移動卡片的 `order-key`；實作放在 `.cljc` 並充分測試。
- **label 一經建立就不變。** 表格、圖在建立時產生 label，前綴 `tab:`、`fig:`，後接建立時給的代稱（英文小寫字母、數字與連字號，例如 `tab:ridership`），沒給代稱時自動產生 4 碼短 id（例如 `tab:k3f9`）；label 在報告內不能重複，重複時拒絕並說明。重新生成、移動都不改，只有使用者明確改名時才變（改名功能之後提供；2026-10-29 使用者決定命名方式）。
- **本文的引用要抽出來存。** `prose` 中的事實引用、實體引用、來源引用，存檔時在同一筆交易中寫入 `:node/facts`、`:node/rows`、citation，讓「哪些段落用到這個事實」是一般 Datalog 查詢。
- **修訂只增不改。** 每次內容變更都屬於一個修改組；復原是新增一個反向的修改組，不刪除歷史。
- **前後端同步。** 前端以 `.cljc` 純函式算出新狀態，比較上次儲存的狀態（`knot.sync/diff`），只送出變動的卡片、關係、素材、事實；後端以一筆交易寫成一個修改組，並記下每個實體修改前後的快照。結構類的修改立即送出；逐字輸入在停止約 0.8 秒後送出，成為一個「編輯文字」修改組。
- **狀態轉換：** agent 寫入本文後轉為 `:ai`；人工改本文後轉為 `:human`。狀態只記錄最後是誰寫的本文，不限制寫入。引言以 agent 撰寫為主，不套用這組狀態。
- **agent 直接寫入。** agent 的寫入像直接 push：立即生效、畫面標示（5.13）、記在卡片歷程、可以比較與復原；使用者自己寫的 `:human` 段落也一樣（5.4 覆寫規則）。不讓寫入送審，理由與不提供鎖定相同：agent 調整結構常一次動多張卡片，逐一審查會讓雙方都卡住；使用者要保留自己的寫法時，以待辦或意圖交代 agent（2026-10-29 使用者決定）。
- **不提供鎖定。** 報告是一個整體，一張卡片改變時其他卡片都應能配合調整；鎖定會破壞這個關係，而每次修改都有修改組與前一版可以檢視與復原，所以不需要鎖定（2026-10-27 使用者決定移除）。舊資料中的 `:locked` 寫入時視為 `:human`。
- **agent 與使用者走同一條寫入路徑。** MCP 工具的寫入經過與畫面相同的合法性檢查（`tree/accepts?`、malli），寫成 `:changeset/by :agent` 的修改組，在畫面上可以看到、比較與復原。
- **段落關係的方向：** 相鄰關係由前一段指向後一段；不相鄰關係由本段（from）指向目標段落（to），例如「本段依據目標段落」。

## 5. 功能規格

每個模組列出行為與驗收條件。驗收條件中的「測試」不呼叫任何模型：agent 的操作以直接呼叫 MCP 工具模擬，agent 交回的內容與其他資料一律使用 `test-resources/fixtures` 的虛構內容。

### 5.1 報告與範本

- 建立報告：空白，或從範本建立。範本的骨架會產生各層標題卡片與契約項目，並把標題對應到契約項目。
- 建立時選擇文風設定，把規則快照存進 `:report/style-snapshot`。
- **目前：** 開啟沒有報告的目錄時建立空白報告（名稱取自目錄名稱），畫面提供「新增第一章」與開發用的「匯入範例內容」。範本與文風待 5.7 的 EDN 格式定案後實作。
- **驗收：** 從 fixture 範本建立的報告，卡片樹結構、編號、契約對應都符合預期。

### 5.2 素材庫

- **匯入流程：** 原始檔複製到 `sources/`，以 anydoc 轉成 Markdown，後端再把 Markdown 切成區塊。解析不在 JVM 內做，因為 Clojure 生態缺少好用的文件解析套件。匯入有兩條路：使用者在素材庫直接匯入檔案或 Markdown；或 agent 依匯入 skill 讀原始檔、整理成符合下方約定的 Markdown，再以 MCP 的 `import_markdown` 匯入（可依章節分批匯入同一個來源檔）。
- **轉換工具：** anydoc 是純 Rust 實作，不需要模型、可離線使用，支援 doc、docx、xls、xlsx、ppt、pptx、OpenDocument、RTF、EPUB、CSV、PDF。以 npm 開發相依安裝並固定版本，後端用子行程執行 `node_modules/.bin/anydoc <檔案>`，讀取 stdout。轉換失敗時依錯誤類型（不支援、加密、檔案損壞）顯示對應提示。
- **使用者可自行提供 Markdown：** 轉換結果不理想時，使用者可以修改轉出的 Markdown 再匯入；也可以直接匯入自己寫的 Markdown、純文字或 CSV。
- **Markdown 約定：** 後端解析 GFM 的標題、段落與表格（`knot.ingest/markdown->blocks`）。標題成為區塊的分組與標題來源；每個表格成為一個表格區塊；少於 8 字的短行（頁首、頁碼）不成為區塊。頁碼以 `<!-- page: N -->` 標記表示：anydoc 轉換 PDF 時不保留換頁位置，所以頁碼標記只來自使用者手寫或修改的 Markdown，否則區塊位置以所屬標題表示。anydoc 輸出的標題層級依字級推測、不可靠，只用來分組，不直接產生卡片樹。
- **文字正規化：** anydoc 的中文輸出含相容字（例如 CJK 部首補充字），建立區塊與搜尋時以 NFKC 正規化。
- **掃描 PDF：** anydoc 不處理只有圖片的 PDF，本工具也不使用雲端 OCR。遇到時提示使用者改提供文字版，或自行轉成 Markdown。
- **M5 開始前的驗證：** 請使用者準備代表性檔案（含表格的中文 PDF、.doc、表頭有合併儲存格的 .xlsx）實際轉換，記錄 PDF 換頁位置是否保留、中文與表格品質、合併儲存格的輸出方式，寫進 `docs/ingest-evaluation.md`。PDF 已完成（結果見上方兩點），.doc 與 .xlsx 待測。
- **候選區塊：** 解析結果一律是 `:candidate`。使用者可以確認、修改、合併相鄰段落、捨棄。
- **需要判斷的整理交給 agent：** 修正標題層級、補頁碼標記、接回被換頁切斷的段落、去除頁首頁尾、把散在文字中的列舉整理成表，都由 agent 依匯入 skill 在匯入前完成，Knot 不內建 AI 切分。agent 匯入的區塊一律是候選。
- **逐字比對：** 匯入整理過的 Markdown 時，每個區塊與 anydoc 對原始檔的輸出比對（NFKC 正規化、忽略空白差異），結果記在 `:block/verbatim`；找不到原文的區塊在素材庫標示；表格的數字逐格比對。比對不通過時的處理方式（擋下、警告或逐一決定）待定。
- **表格編輯：** 改欄名、設定欄位型別（文字、數字、日期），把表設為實體表並指定名稱欄。
- **事實綁定：** 在儲存格上建立事實，輸入 key、標籤、單位。
- **連結到段落：** 素材庫是獨立頁面，不與卡片樹並排。段落的依據在段落編輯區以「搜尋或選取」加入：開啟素材選取器，以全文搜尋與類型、狀態篩選找到區塊後加入；素材庫頁面的區塊詳情列出引用它的段落，可跳回段落編輯。不以拖曳連結。
- **搜尋：** Datalevin 全文搜尋區塊標題與內容，可依類型、狀態篩選。Datalevin 預設的分詞器以空白切詞，不適用中文，必須自訂分析器，例如中文字元以二元組（bigram）切分。
- **驗收：** fixture 的 docx、xlsx、pdf 經 anydoc 轉換後，產生正確的段落與表格區塊；含頁碼標記的 Markdown 產生帶頁碼的區塊；改寫過字句或數字的 Markdown 被逐字比對標出；轉換失敗顯示對應提示；搜尋「節電」能找到含「節電率」的區塊。

### 5.3 卡片樹

- **層級：** 標題最多四層，例如第三章、3.1、3.1.1、3.1.1.1，各層稱為「章、節、項、款」。每個標題底下可以有一張選用的**引言**卡片，概述這一層的內容或說明其目的；引言最多一張，固定排在最前面，卡片上標示「引言」，標題的編輯區提供「新增引言」；引言的本文由 agent 依該層下層內容撰寫（見 5.4），使用者也可以先寫下意圖。引言之後，標題底下依序是這一層直接的段落（可以沒有），接著是下一層標題（可以沒有）：段落與下層標題可以並存，但段落一律排在下層標題之前，不能出現在下層標題之後（全文中標題之後的文字屬於該標題）。已有段落的標題可以直接新增下層標題，接在段落後面（2026-10-29 使用者決定，取代原本「兩者不混用」）；仍提供「把現有段落移到新的下層標題」與「把某段改為引言」。表格與圖只能掛在段落底下。拖曳時，插入位置的 parent 必須能容納該類卡片；移入時放在同類卡片的最後。拖曳只在同一層進行（見下方「拖曳」），因此標題的層級不會因拖曳而改變；跨層移動之後另以「移到…」選單提供。
- **依深度分欄：** 第 n 欄顯示樹中深度為 n 的所有卡片，不分類型，依 parent 分組，組間留較大間距；同一欄可能同時有標題卡片與段落卡片，以樣式區分（標題有左側深色條與灰藍底，段落白底，引言虛線，表與圖淡暖底）。欄位名稱依內容決定：標題用該層稱呼，另有段落、表與圖時一併列出，例如「項／段落」。最多六欄（四層標題、段落、表格與圖）；欄寬依看板全寬均分、每欄至少約 195px，放不下時水平捲動；編輯區以抽屜覆蓋，不影響欄寬；選取時水平捲動，讓選取卡片所在欄與其上、下一欄都在可視範圍內。卡片顯示標題與最多兩行摘要；尚未生成本文的段落另顯示「尚未生成」標籤；有未完成待辦的卡片顯示待辦數（5.11）。agent 撰寫、人工改過不另加標籤（狀態仍記錄）。
- **選取與透明度：** 選取卡片為白底、2px 深藍框；其祖先與子孫為淡藍底實色；同一 parent 的兄弟透明度 0.7；其他卡片 0.35。
- **選取置中：** 選取後每欄各自垂直捲動，讓相關卡片對齊欄位中線：祖先欄對齊該祖先；同層欄對齊選取的卡片；子孫欄對齊所有子孫的整體範圍；沒有子孫時對齊它們在樹中應有的位置；範圍高於可視區時改為頂端對齊。動畫約 0.45 秒，並遵守 `prefers-reduced-motion`。
- **拖曳（只在同一層）：** 整個欄位都是放置區，不必對準卡片：在同一欄（同深度）依指標高度取最近的合法間隙插入，並顯示插入線（組與組之間的間隙，靠近上方卡片底緣是接在它後面、靠近下方卡片頂緣是插在它前面）；在左邊一欄（深度少一）移入指標所在或最近的卡片，成為最後一個子卡片，該卡片顯示虛線框，可用於移到其他 parent 或還沒有子卡片的標題。拖曳中標示可放置的兩欄、其他欄淡出；按 Esc 取消。介面不放操作說明文字。不能拖到自己或自己的子孫，其餘合法性依上方的層級規則判斷。拖曳時指標靠近欄位上下緣，該欄自動捲動。
- **鍵盤替代：** Alt+↑／↓ 上移、下移選取的卡片。
- **移動之後：** 被移動的卡片成為選取狀態；編號重算；若是段落，舊位置的下一段、被移動的段落、新位置的下一段，與前一段的關係都標為待確認；顯示一行訊息說明變動；整個移動是一個 `:move` 修改組，可復原。
- **新增與刪除：** 卡片樹上方只有「新增」與「刪除」，都作用在選取卡片的層級上：「新增」在選取卡片後面加一張同類卡片（標題或段落；選取引言時新增段落，接在引言後面），新卡片立即選取並進入名稱編輯；「刪除」連同下層卡片一起刪除，可復原。空標題底下的第一張卡片與引言，從標題編輯區的「下層內容」新增。表格與圖從段落編輯區「下層表與圖」的「新增表格」「新增圖」新增（label 自動產生）；選取表格或圖時，「新增」在它後面加一張同類卡片。
- **字數：** 字數是本文去掉空白後的字元數（事實以代入的值計算，清單的編號與符號不算，表格與圖不算）；標題的字數是底下所有段落與引言的合計。卡片可設定選填的目標字數（篇幅），標題的目標是整章／整節。段落與引言卡片在名稱列右側顯示字數，有目標時顯示「字數／目標」；標題卡片顯示合計。實際字數低於目標的 80% 或超過 120% 時以顏色提示（不足、超出），沒有本文時只顯示目標。編輯區：段落、引言、標題的設定區有「目標字數」欄位（數字，可清空），本文區標題旁顯示字數。全文頁的大綱不顯示字數（使用者決定）。agent 以 `get_outline`、`get_card` 取得字數與目標，`get_writing_context` 在本段帶目標字數，`add_card`、`build_outline`、`update_card` 可設定目標字數（2026-10-29 使用者決定）。
- **捲動：** 頂部列固定，卡片樹與編輯區各自捲動；滾輪在卡片欄位上時只捲動該欄，不捲動整頁。窄螢幕時各區依序排列，回到整頁捲動。
- **鍵盤：** 方向鍵在卡片間移動（左右換層、上下換兄弟）。移動卡片只用拖曳與 Alt+↑／↓，編輯區不提供上移、下移按鈕。Esc：在輸入框或本文中先結束編輯，否則收合編輯區。在輸入框以外按 Ctrl／⌘+Z 復原（5.10）。
- **驗收：** 編號、分數索引、拖曳合法性、關係標記都有單元測試；畫面行為由使用者對照設計稿確認。

### 5.4 段落詳情與撰寫

- **段落關係：** 相鄰關係（遞進、因果、對比、舉例）只在同一標題下前後相接的段落之間，移動後標為待確認。不相鄰關係可連到任意距離的段落，類型為摘要（本段彙整目標的結果）、依據（本段論點建立在目標的結果上）、呼應、對比；在段落編輯區以「新增關係」選類型並搜尋目標段落建立。選取段落時，卡片看板以虛線框標出與它有不相鄰關係的卡片。
- **段落編輯區：** 標題列是名稱與「⋯」選單（結構操作，例如「改為引言」，之後的「移到…」也放這裡）。內容依撰寫的流程由上而下分成四個固定區塊：
  1. **生成依據**（在這張卡片上設定的，唯一要輸入的地方；使用者與 agent 都可以寫）：意圖（這段的重點）；依據（引用的素材，以搜尋或選取加入）；關係（與前一段、後一段的相鄰關係類型與確認待確認的關係，以及本段新增的不相鄰關係）；下層表與圖。
  2. **撰寫時參考的內容**（自動組成，只能看；即 agent 以 `get_writing_context` 取得的內容）：依「上層、本段、鄰近、下層、關係、素材、文風」分組列出摘要，每一項標明帶的是本文還是意圖，展開可看全部內容；其他段落指向本段的關係（例如被摘要）也列在這裡。
  3. **本文**：本文，以及「目前內容／與前一版比較」切換。要 agent 撰寫時，在「留言與歷程」新增待辦（5.11）。
  4. **留言與歷程**（5.11 與下方「卡片歷程」）：這張卡片的留言串、待辦與修改紀錄依時間穿插，可新增留言。

  視覺上以表面區分區塊的角色：生成依據是白底表單，撰寫時參考的內容是淡藍底的唯讀面板，本文以白色紙張樣式呈現。標題列固定在抽屜頂端，顯示名稱；尚未生成的段落在名稱旁標示「尚未生成」。欄位的新增操作（加入依據、新增關係等）是欄位標題右側的文字按鈕，不用整列按鈕。意圖與本文用同一種編輯框（高度隨內容）：平常是淡底的閱讀樣式，滑過時提示「點擊編輯」；點進去後是白底藍框並標示「編輯中 · Esc 結束」，按 Esc 結束編輯（再按一次才收合編輯區）。關係預設唯讀（類型是標籤、沒有移除與新增），按欄位右側的「編輯」後整個欄位進入編輯狀態，才能改類型（相鄰與不相鄰關係都可以；不相鄰關係改類型是一次可復原的「變更關係類型」）、確認、移除與新增，按「完成」離開；換卡片時回到唯讀。依據、關係、下層表與圖用同一種底色項目列：開頭是完整的類型標籤（段落、表格、依據、呼應…），接著名稱，右側是來源等補充資訊與操作。關係列依序是「關係類型、位置、卡片名稱」：相鄰關係的類型以下拉選單直接放在開頭，位置寫「前一段／後一段」；不相鄰關係的位置是目標段落所屬標題的編號（例如 1.2.1，章底下的段落寫「第一章」）。不用數字標示區塊順序，避免與看板欄位的層級編號混淆。
- **與前一版比較：** 本文區可切換為修改前後的差異，比較目前的本文和最近一次修改之前的本文；最近一次修改由 agent 所做時標明「agent 修改」（刪除的字以紅色刪除線、新增的字以綠色底線標示）。連續的逐字輸入（相隔 10 分鐘內的「編輯文字」修改組）算同一次修改；建立卡片不算修改。前一版取自修改組的修訂快照（`GET /api/report/nodes/:id/previous`）。這是「卡片歷程」中最近一筆本文修改的捷徑。
- **卡片歷程：** 參考 GitHub issue 頁面的時間軸，「留言與歷程」區塊把這張卡片的修改紀錄與留言串依時間穿插，最新的在下方，讓「這段為什麼長這樣」可以追溯（2026-10-29 使用者決定；取代原本「只保留前一版，不提供版本清單」）。介面用語仍是「留言」「修改」，不用 issue、commit。
  - 每筆修改紀錄列出：修改者（agent／使用者）、修改組名稱、時間、改了哪些內容（名稱、意圖、本文、依據、關係、位置、狀態）。名稱與意圖的變動直接列出修改前後的文字。
  - 有本文變動的紀錄有「看差異」：本文區切到比較模式，顯示那次修改前後的差異（不是和目前比較）。
  - 連續的逐字輸入與「與前一版比較」相同，合併成一筆。建立卡片是第一筆；匯入的卡片以「匯入」作為第一筆。已復原的修改標示「已復原」，復原本身也列為一筆。
  - 預設顯示最近 10 筆修改紀錄，較早的以「顯示較早的紀錄」展開；留言一律顯示。
  - 修改紀錄取自修改組的修訂快照（`GET /api/report/nodes/:id/history`；某次修改的本文前後：`GET /api/report/nodes/:id/changes/:changeset-id`）。只有卡片層級的歷程，不提供整份報告的時間軸（使用者決定；整份報告的近況看頂部列的「最近修改」）。
- **標題、引言、表與圖的編輯區** 沿用相同的區塊樣式，最後都有「留言與歷程」：標題為「設定」（意圖、契約項目）與「結構」（引言、下層內容）；引言為生成依據（意圖，可留空）、撰寫時參考的內容、本文；表與圖為「設定」（意圖、label、圖檔）。
- **輸入即意圖：** 為卡片寫下的內容（標題名稱、意圖、關係類型與說明）都是該卡片的提示詞，存在卡片上，不直接出現在報告成品中；agent 規劃結構時寫下的意圖，使用者可以直接修改。撰寫某一段時，周邊卡片**一律只帶意圖**：撰寫參考的內容保持精簡，agent 需要銜接或用到某張卡片的結果時，再以 `get_card` 取得它的本文（2026-10-29 試寫後使用者決定，取代原本「有本文就帶本文」；試寫時 27 段的撰寫參考合計約 38KB，重複多）。例外是引言：引言摘要下層內容，下層有本文時帶本文。
- **撰寫時參考的內容（`knot.context/generation-context`）：**
  - 上層：章節路徑及各層標題的意圖；所屬標題的引言的意圖。
  - 本段：本段意圖；下層表格與圖的 label 與意圖。
  - 鄰近：前一段、後一段的意圖與相鄰關係類型，並標明對方是否已有本文。
  - 關係：不相鄰關係的目標段落帶意圖，並標明是否已有本文（摘要、依據要用到目標的結果，agent 以 `get_card` 取本文）；以摘要關係連到本段的段落帶意圖。
  - 素材：引用區塊的內容；引用表格的欄位與相關列；引用素材上的事實（key、標籤、值、單位），不帶整份報告的事實。
  - 文風：文風規則。組裝邏輯寫成 `.cljc` 純函式，編輯區的預覽與 MCP 的 `get_writing_context` 共用同一份結果。
- **引言的撰寫：** 引言主要由 agent 補上。輸入改為標題名稱與意圖、引言的意圖（可留空），以及這一層的下層內容（下層標題或段落，有本文帶本文，否則帶意圖）。引言適合在下層內容大致完成後才生成；下層還沒有本文時，介面提示這一點。
- **撰寫流程：** agent 以 `get_writing_context` 取得上述內容，依撰寫 skill 寫好本文，以 `write_prose` 交回。一次撰寫多段時，agent 依卡片樹順序逐段進行。
- **交回格式：** 本文為純文字，每一行是一段（空行忽略）；以「- 」開頭的連續行是項目清單，以「1. 」這類數字加句點開頭的連續行是編號清單（編號由 Knot 依順序產生），清單只有一層。以標記表示引用：`{{fact:key}}`、`{{ref:label}}`、`[[cite:block-id]]`。Knot 轉成 ProseMirror JSON（段落、項目清單、編號清單）；`get_card` 以同樣格式回傳本文，方便 agent 修改後交回。
- **列點：** 清單是本文的一部分，不是獨立卡片（2026-10-29 使用者決定）：適合「主要成果如下：」接數點的寫法。本文編輯器支援清單：行首輸入「- 」或「1. 」開始清單，空項目按 Enter 結束清單。全文與 LaTeX 匯出輸出為項目或編號清單。
- **表格：** 表格卡片的內容由 agent 以 `write_table` 交回欄名與各列（例如自行整理的「指標達成總表」），存在卡片上，編輯區與全文頁顯示表格；儲存格的數字不列入「未綁定的數字」。素材表（M5）接上後，表格也可以由素材表產生，兩種來源並存（2026-10-29 使用者決定）。使用者要改表格時以待辦交代 agent（直接編輯儲存格之後再提供）。
- **圖：** 圖卡片目前只有名稱、意圖與 label，畫面顯示佔位；圖檔在 LaTeX 匯出（M8）時處理（2026-10-29 使用者決定）。
- **驗證（在 Knot 內）：** 標記中不存在的事實、label、區塊一律拒絕寫入，並把原因回傳給 agent 修正；本文中不在標記內的數字，寫入後標為「未綁定的數字」提醒使用者，也回傳給 agent。「未綁定的數字」由本文即時算出、不另外儲存，在本文區下方列出；年、月、日與章節編號（例如 114 年、3 月、2.1.1）不算；報告還沒有任何事實時（素材接上之前）不提醒，畫面與 agent 都不列（2026-10-29 試寫後使用者決定）。`[[cite:block-id]]` 引用的區塊同時加入這段的依據。
- **覆寫規則：** 不論目標的狀態，agent 一律直接寫入，狀態轉為 `:ai`；改到 `:human` 段落時，卡片歷程與「與前一版比較」標明「agent 修改」，使用者可以比較與復原（2026-10-29 使用者決定，取代原本「`:human` 段落改成修改建議」）。
- **人工編輯：** 本文區即是 Tiptap 編輯器，可直接修改（尚未生成時也可直接撰寫）；改了意圖或本文就觸發 5.6 的連動；改了本文轉為 `:human`。逐字輸入與意圖一樣在停頓約 0.8 秒後存成「編輯文字」修改組。
- **驗收：** 以 `write_prose` 交回的 fixture 本文產生事實引用節點；含清單的本文轉成清單節點，`get_card` 回傳的文字與交回的相同；`write_table` 的內容在編輯區與全文頁顯示；重複或格式不對的 label 被拒絕；不存在的標記被拒絕並回傳原因；含裸數字的本文產生提醒；寫入 `:human` 段落後狀態轉為 `:ai`，前一版可以比較與復原。

### 5.5 事實

- 事實的值：綁定儲存格時讀取該格，否則用 `:fact/value`。
- 本文中的事實引用在顯示與匯出時才代入值，所以改事實不需要修改任何本文，也不需要審查。
- 事實的值改變時，列出引用它的段落讓使用者知道，但不產生待辦。
- **驗收：** 修改來源表儲存格後，引用該事實的段落顯示新值。

### 5.6 相關段落的連動

使用者改了一段之後，依賴它的段落（摘要它的段落、上層的引言、以它為依據的段落）可能也要跟著改。內部稱為「擴散」，介面上不用這個詞，使用者只看到「相關段落有待辦」。

判斷與修改需要模型，交給 agent；Knot 只負責找出受影響的段落並留下待辦。agent 與其他寫入一樣直接修改，不經審查（2026-10-29 使用者決定，取代原本「修改建議、審查畫面、整組接受」的做法）。

1. **找出受影響的段落（Knot）：** 使用者存了段落的意圖或本文後，以 Datalog 規則查詢。摘要依賴：有 `:summarizes` 關係指向此段的段落，以及此段所有上層標題的引言（引言對其所屬層的摘要依賴是隱含的，不另存關係）。論證依賴：下一段（若關係為因果或遞進），以及以「依據」關係指向此段的段落。「呼應」「對比」不構成依賴。
1. **留下待辦（Knot）：** 每個受影響的段落新增一則 Knot 寫的待辦（`:note/author :knot`），說明哪一段改了、兩者的關係，例如「「1.2 背景」的本文改了，本段摘要它，可能需要跟著更新」，並記下觸發的卡片與依賴類型。同一個目標已有同一張觸發卡片的未完成待辦時不重複新增（連續輸入只留一則）。
1. **處理（agent）：** agent 以 `list_todos` 取得這些待辦，以 `get_card` 的修改紀錄看觸發的卡片改了什麼，判斷是否需要修改：需要時直接寫入，以 `complete_todo` 附上回覆並連到修改組；不需要時同樣以 `complete_todo` 回覆原因。
1. **只連動一層：** 只有使用者的修改會觸發；agent 的寫入不觸發，agent 修改多段時自行顧及一致性（可用 `get_writing_context` 看關係）。
1. **沒有 agent 時：** 這些待辦就是「待處理的相關段落」清單，使用者可以自己修改目標段落，或直接標為完成。

- **畫面：** 沿用 5.11 的留言與待辦：卡片待辦數、頂部列待辦清單、編輯區的留言串；Knot 的待辦標示為「Knot」。修改後在卡片歷程看 agent 改了什麼，可以比較與復原。
- **驗收：** 使用者修改段落後，摘要依賴與因果依賴的段落產生 Knot 待辦，呼應與對比不產生；連續修改不重複產生；agent 的寫入不觸發；以 MCP 完成待辦並連到修改組。

### 5.7 文風設定

- 規則清單可新增、編輯、刪除，每條規則有類別、說明、範例。
- 分層合併：公司 < 機關 < 專案，同 id 的規則由下層覆蓋。
- 共用的文風與範本存成 EDN 檔，放在使用者設定目錄：`~/.knot/styles/`、`~/.knot/templates/`（不另設共用資料庫）。檔案格式待使用者提供範例後定案。
- 套用到報告時存成快照；設定目錄中的來源檔更新後，報告顯示「文風設定有更新」並提供同步。
- 從範例文字萃取規則由 agent 依 skill 進行，以 MCP 寫入規則，放在 M10。
- **驗收：** 合併結果與快照內容有單元測試。

### 5.8 交接檢查

- **一致性：** 本文中出現實體的別名寫法卻未使用實體引用（別名由使用者在實體表維護）；本文中未綁定的數字。
- **契約涵蓋：** 沒有任何卡片對應的契約項目。
- **缺少依據：** 有本文但沒有引用的段落；引用了未確認區塊的段落。
- 以上檢查都是確定性的，做在 Knot 內，也以 MCP 的 `find_issues` 提供給 agent。語意上的一致性（前後說法矛盾、用語不一）可請 agent 檢查，結果寫成卡片上的留言。
- 每個項目可以跳到對應卡片；匯出時可選擇轉為待辦標記。
- **驗收：** fixture 報告中預先埋好的每類問題都被找出。

### 5.9 LaTeX 匯出

- **專案結構依使用者的範例專案，屬待定事項。** 範例到位前先採用：每章一個 `chapters/chNN.tex`，表格各自一個 `tables/<label>.tex`，圖檔複製到 `figures/`；主檔由使用者提供，工具不產生。
- **章節檔：** 四層標題依序輸出為 `\chapter`、`\section`、`\subsection`、`\subsubsection`（第四層是否編號取決於使用者 .cls 中 secnumdepth 的設定）；引言緊接在標題指令之後輸出，段落之間空一行；事實代入值與單位；交互參照依類型輸出為 `表~\ref{tab:…}`、`圖~\ref{fig:…}`；段落之後依序輸出子表格的 `\input` 與圖的 figure 環境。
- **跳脫：** `% $ & # _ { } ~ ^ \` 都要正確跳脫，全形字元不處理。
- **表格檔：** 由表格視圖確定性產生，預設 booktabs；檔案開頭註明由工具產生、來源表與匯出時間，請勿手動修改。
- **選項：** 段落追溯註解 `% node:<uuid> src:<block-ids>`；交接檢查的未解決項目轉為 `\todo{}`（使用者的範例需載入 todonotes）。
- **局部匯出：** 只寫入選取的章節或表格，不刪除其他檔案；目標檔存在且不是工具產生的檔案時，先詢問才覆寫。
- **驗收：** 以 fixture 報告做 golden file 測試，比對輸出的 `.tex` 字串；跳脫有單元測試。能否編譯由使用者自行驗證。

### 5.10 復原

- 在本文編輯器以外按 Ctrl+Z 或 Cmd+Z，復原最近一個尚未復原的修改組，不論來源是手動、移動、重新生成或 agent；先送出尚未儲存的輸入。匯入與復原本身不在復原範圍。復原的提示列出修改組名稱，agent 的修改組標明「agent」。屬於一組的修改組（見 5.12 的 `group`）整組復原：每個實體還原為組內最早一筆修改之前的內容，只新增一個復原修改組。
- 本文編輯器內使用 Tiptap 自己的復原。
- **驗收：** 每種來源的修改組都能復原，復原後資料與修改前一致。

### 5.11 留言與待辦

卡片上的留言是使用者與 agent 之間的溝通管道：agent 在畫面上寫給使用者看，使用者也在畫面上交代 agent。

- **留言：** 每張卡片有一串留言，使用者與 agent 都可以新增與回覆；也可以留在整份報告上（不屬於任何卡片）。留言不出現在報告成品中，也不屬於撰寫時參考的內容。
- **待辦：** 使用者的留言可以標為待辦，表示要 agent 處理，例如「這段重寫得精簡一點」「把這兩段合併」「補上 2025 年的數據」。不另設「請 agent 撰寫」按鈕，由使用者自己寫待辦（2026-10-27 使用者決定）。待辦狀態為未完成或已完成；agent 處理後標為已完成並回覆說明，記下它所做的修改組，使用者可以從留言跳到「與前一版比較」。使用者也可以自己把待辦標為已完成或重新打開。
- **agent 的提問：** agent 不確定時以留言提問（例如意圖不清楚、素材互相矛盾），使用者在畫面上回覆。
- **畫面：** 編輯區最後一個區塊「留言與歷程」列出這張卡片的留言串，與修改紀錄依時間穿插（5.4「卡片歷程」），最新的在下方，待辦有勾選框；卡片樹與全文大綱上，有未完成待辦的卡片顯示待辦數；頂部列有「待辦」入口，列出整份報告未完成的待辦與 agent 的提問，點擊跳到卡片。
- **與修改組的關係：** 新增、完成留言不是內容修改，不進修改組、不在 Ctrl／⌘+Z 的復原範圍；刪除留言只限作者本人的留言。
- **agent 的提問：** agent 寫的留言（不是回覆）還沒有人回覆時，視為提問，列在頂部列的「待辦」；使用者回覆後不再列出。
- **整份報告的留言：** 不屬於任何卡片，列在頂部列「待辦」打開的清單中，也在那裡新增。
- **不提供修改留言**，只能新增、回覆、刪除自己的留言（刪除時連同它的回覆）。
- **卡片刪除時：** 留言保留但不顯示、不計入待辦；卡片復原後重新出現。
- **沒有 agent 時：** 留言照常可用，作為使用者自己的備忘與待辦清單。
- **驗收：** 以 MCP 讀取未完成待辦、回覆並標為完成；完成的待辦連到修改組；卡片的待辦數正確。

### 5.12 agent 介面（MCP 與 skill）

**原則**

1. **agent 是另一位使用者，不是後門。** 所有寫入走與畫面相同的檢查與修改組（第 4 節「資料規則」）。
2. **工具以使用者會做的事為單位，** 不是資料表的 CRUD：例如「在 3.1 底下、某段之後新增段落並寫上意圖」，編號、分數索引、關係的待確認標記由 Knot 處理。
3. **agent 的產出要經過使用者。** agent 匯入的素材是候選；agent 寫的本文狀態為 `:ai`；每次寫入都記成修改組，使用者可以比較與復原。
4. **每個寫入工具接受 `summary` 參數，** 作為修改組名稱（例如「建立第三章骨架」）。
5. **多次寫入可以算成一次修改：** 寫入工具接受選填的 `group`（組名）。連續的寫入傳相同的組名時，Knot 把它們歸為一組：卡片歷程與「最近修改」顯示為一筆（名稱用組名），Ctrl／⌘+Z 一次復原整組。延續條件：資料庫中最近一個修改組是同組名、同為 agent、相隔不超過 30 分鐘且未被復原；中間有使用者或其他寫入、換組名、超過時間就開始新的一組（2026-10-29 試寫後加入）。
6. **參數名稱一致：** 指定要操作或查詢的卡片一律用 `card_id`，留言一律用 `note_id`；其他卡片以用途命名（`parent_id`、`after_id`、`target_id`、`from_id`、`to_id`）。回傳也用同樣的名稱（2026-10-29 試寫後加入）。
7. **卡片名稱不含編號：** 工具回傳的 `title` 是純名稱，編號（「第一章」「1.2」）在 `number`，由位置決定。
8. **錯誤要能讓 agent 自行修正：** 不合法的位置、不存在的標記、版本衝突，都回傳可讀的原因與目前狀態。

**工具**（名稱與參數在實作時定案，依里程碑逐步加入）

| 類別 | 工具 |
|---|---|
| 讀取 | `get_outline`（卡片樹：id、類型、編號、名稱、意圖摘要、狀態、待辦數；`full_intent` 時帶完整意圖）、`get_card`、`get_cards`（一次多張，最多 30 張）、`get_writing_context`、`find_issues` |
| 報告 | `update_report`（名稱、副標） |
| 卡片 | `add_card`（標題、段落、引言、表格、圖）、`build_outline`（一次建立巢狀骨架）、`update_card`（名稱、意圖）、`move_card`、`delete_card`（連同下層卡片）、`set_relation`、`add_remote_relation`、`remove_relation`、依據的新增與移除 |
| 本文 | `write_prose`（段落與引言的本文，5.4）、`write_table`（表格卡片的內容） |
| 留言 | `list_todos`、`add_note`（留言或回覆）、`complete_todo` |
| 素材 | `search_sources`、`get_source_block`、`import_markdown`、`create_fact` |

- **agent 可以刪除。** `delete_card`、`remove_relation` 與其他寫入一樣記成 agent 的修改組，使用者可以檢視與復原，因此不另外限制（2026-10-27 使用者決定）。`delete_card` 可附上版本，避免刪掉使用者剛改過的卡片。

**skill**（放在 repo 的 `skills/`，隨 Knot 發佈，與工具一起改版）

- **規劃：** 讀報告目錄中的資料，提出結構與每張卡片的意圖，與使用者討論後以 `build_outline` 建立。
- **匯入：** 整理原始檔成 Knot 的 Markdown 約定（5.2），以章為單位分批匯入，不得改寫原文。
- **撰寫：** 依卡片樹順序取得撰寫內容、撰寫、交回；處理未完成的待辦（含 Knot 為相關段落留下的待辦，5.6）。

**對象：** 初期只支援 Claude Code。是否支援其他 MCP 用戶端（把 skill 內容也放進 MCP 的 prompts）待定。

- **驗收：** 每個工具有測試：以 JSON-RPC 呼叫 `/mcp`，檢查回應與寫入的修改組；`Origin` 不是 localhost 的請求被拒絕；使用者以 Claude Code 連上後，請 agent 依虛構素材建立一章骨架並撰寫一段。

### 5.13 畫面同步

agent 在背景寫入時，畫面要即時反映，也不能把 agent 的修改蓋回去。

- **通知：** 後端提供 `GET /api/events`（Server-Sent Events）。任何修改組或留言寫入後送出通知（修改組 id、來源、影響的卡片）。前端收到後重新讀取報告：使用者沒有在輸入時立即以 `ui/replace-data` 更新（與復原後的做法相同）；正在輸入的卡片先保留，結束輸入並送出後再更新。
- **衝突檢查：** 前端送出卡片修改時附上它所依據的 `:node/version`；後端發現版本已被其他來源改過時拒絕整個修改組（回應 409 並列出衝突的卡片；檢查與寫入在同一個鎖內完成，刪除與復原不檢查），前端重新載入並提示「這張卡片剛被 agent 修改」，使用者的輸入保留在提示中可以複製。agent 的寫入工具同樣檢查版本（`get_card` 回傳版本，寫入時可附上）。
- **agent 的修改在畫面上：** agent 修改的卡片顯示綠色框（與選取的深藍框同樣粗細，標題卡片左側的色條一起變綠），約 3 秒後漸漸淡回原本的樣子。
- **最近修改：** 頂部列的「最近修改」（在「待辦」旁邊，每一頁都有）列出最近修改的卡片，不分 agent 或使用者，標明修改者（最多 10 張，每張只列最近一次的修改組名稱與時間；段落前加上所屬標題；匯入與復原本身不算修改，已刪除的卡片與已復原的修改組不列；`GET /api/report/recent-changes`），點選跳到卡片（在素材庫時切到卡片頁）。
- 這套機制也處理同一份報告開在多個分頁的情況。
- **驗收：** 以 MCP 寫入後，開著的頁面在 1 秒內更新；同一張卡片在畫面與 MCP 同時修改時，後到者被拒絕且不遺失先到的修改。

## 6. 介面設計稿位置與畫面規格

設計稿的正本放在 claude.ai，repo 裡放匯出的圖檔與索引。Claude Code 讀 repo 內的檔案，不直接開 claude.ai 連結，因為那需要登入。

**01 主編輯畫面**（`01-main-editor.png`）

- 頂部列：左側為報告名稱與副標（單行，過長時截斷），中間為置中的三個頁籤「素材」「卡片」「全文」，右側為「最近修改」（5.13）、「待辦」（5.11）與匯出 LaTeX；交接檢查的入口依第 7 節的里程碑加入。卡片區的標題列依序是「卡片」、選取卡片的位置（上層 › 卡片名稱，過長時省略上層），以及靠右的新增與刪除。「卡片」頁籤即本畫面；「全文」頁籤見下方「全文視圖」；「素材」頁籤見 04。
- 左側卡片樹：依深度分欄，欄寬依看板全寬均分（每欄至少約 195px），行為見 5.3。
- 右側編輯區：覆蓋在卡片看板上的抽屜（約 560px），不擠壓看板；預設收合，點擊卡片只選取、不會自動打開；由使用者點把手展開，新增卡片時自動打開以輸入名稱。可收合（Esc 或收合按鈕），收合後看板右緣留把手顯示選取的卡片、點擊展開。抽屜打開時，看板水平捲動讓選取卡片所在欄與其上、下一欄落在未被遮住的範圍。內容：選取卡片的編輯內容，段落時見 5.4；標題時編輯名稱與意圖，顯示契約項目、引言（可新增）與下層內容；引言時編輯意圖；表格、圖時編輯名稱與意圖並顯示 label。各類卡片的區塊安排見 5.4。
- 寬度不足時兩欄依序換行，卡片樹在自己的容器內水平捲動。
- **全文視圖：** 三欄：
  - 左側大綱：列出所有標題，依層級縮排；選取的卡片所在的章節標為目前位置；點標題即選取並把全文捲到該處。
  - 中間全文：依序呈現整份報告的標題與本文，靠左排列並限制行寬；點標題或段落即選取。從大綱或其他地方選取時，全文捲到該處。
  - 右側編輯區：固定在右側，不覆蓋全文、不收合（卡片頁的編輯區仍是可收合的抽屜）。本文在編輯區修改，存檔寫回對應卡片。

**02 修改建議審查**：不做（2026-10-29 改為 agent 直接寫入，相關段落以待辦處理，見 5.6）。

**04 素材庫**（尚無設計稿）

- 獨立頁面：左側搜尋與篩選（類型、狀態、來源檔），中間區塊清單，右側區塊詳情（完整內容或表格、來源與位置、確認狀態、引用它的段落）。
- 候選區塊在此確認、修改、合併或捨棄；匯入來源檔也在此頁。

**03 交接檢查與 LaTeX 匯出**（`03-handoff-export.png`）

- 左側：一致性、契約涵蓋、缺少依據三組檢查結果，各項可跳到卡片或一鍵修正。
- 右側：匯出目錄預覽（標示工具產生的檔案）、追溯註解與待辦標記選項、整份或局部匯出、章節檔預覽。

**尚無設計稿的畫面**

素材庫（含候選區塊確認、合併與逐字比對結果）、素材選取器、表格編輯、文風設定、報告建立、留言與歷程（編輯區區塊與頂部列的待辦清單）。依上述視覺規範自行設計，先做最簡可用版本，完成後請使用者確認；確認後的畫面也要補進畫布與 `screens/`。

## 8. 開發守則與待定事項

**開發守則**

- **測試不呼叫模型。** Knot 不呼叫 LLM；自動測試以直接呼叫 MCP 工具模擬 agent，交回的內容用虛構 fixture。以真實 agent 試用只在使用者明確要求時進行。
- **只用虛構資料。** repo 內不放任何真實的政府專案素材，fixture 一律虛構（例如「OO 市智慧路燈示範計畫」）。
- **純函式優先放 `.cljc`。** 編號、label、樹運算、合法性判斷、文風合併都寫成純函式，方便前後端共用與測試。
- **新增相依套件要說明。** 在 PR 說明中寫出套件名稱、版本與理由；所有版本都固定，不用範圍或 latest。
- **不擴大範圍。** 第 1 節的範圍外項目不實作；覺得需要時先提出。
- **遇到待定事項就停下。** 列出選項與各自影響，請使用者決定。

**待定事項**

- LaTeX 範例專案：目錄結構、章節與表格的寫法、表格環境（由使用者提供）
- 逐字比對不通過的區塊：擋下、警告或由使用者逐一決定（5.2）
- 是否支援 Claude Code 以外的 MCP 用戶端（5.12）
- agent 可否直接確認素材
- 可執行 jar 的打包細節（啟動方式已定：在報告目錄執行 jar）
- 共用文風與範本的 EDN 檔案格式（由使用者提供範例）
- 從舊報告開始時，舊報告的匯入格式（LaTeX、Word 或 PDF）
- anydoc 驗證：.doc 與表頭有合併儲存格的 .xlsx 的輸出方式（PDF 已完成，見 5.2）
- 範本與契約項目的來源格式（5.1，與文風 EDN 一併定案）

（相依套件的版本已於 M0 固定，記錄在 `CLAUDE.md`。）
