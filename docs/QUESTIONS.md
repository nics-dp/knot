# 待討論問題

每題寫明相關章節、問題、可能的選項與各自影響。定案後更新 `docs/SPEC.md`，再從本檔移除該題。

## Q1. 拖曳時「同層」與「上一層」的判斷（SPEC 5.3 拖曳）

- **問題：** 規格寫「拖到同層卡片上插入前後；拖到上一層的卡片上移入」。但依深度分欄後，同一欄可能同時有標題與段落，字面規則會讓段落無法移到不同深度的標題底下（例如從 3.1 的段落移到 2.2.1.2 底下）。
- **目前實作（選項 A）：** 依目標所在欄判斷——
  - 目標在較淺的欄：移入（目標必須能容納）。
  - 目標在同一欄：優先插入前後；前後不合法時（例如目標的 parent 不收這類卡片）改為移入。
  - 目標在較深的欄：插入前後（標題可因此改變層級，仍受四層限制）。
- **選項 B：** 嚴格照字面，只允許同一欄插入前後、相鄰上一欄移入。跨深度的移動要分多次拖曳，或另提供「移到…」選單。
- **影響：** A 比較靈活，但同一欄的標題卡片可能出現「移入」，使用者需要看虛線框與插入線分辨；B 規則單純但操作較繁瑣。

## Q2. M2 介面先於 M1 資料層完成

- **問題：** 依使用者要求先完成主編輯畫面。目前卡片樹、關係、復原都在前端記憶體運作，資料來自 `test-resources/fixtures/reports/streetlight.edn`（經 `/api/sample-report` 提供，只在 `:dev` 啟動時存在），重新整理頁面就會回到初始狀態。
- **選項：**
  - A. 接著做 M1，把 `knot.tree`、`knot.order-key` 的純函式接上 Datalevin，前端改為透過 API 讀寫。
  - B. 先繼續做其他畫面（M3 素材庫等），M1 之後再一起接。
- **影響：** A 讓後續功能都建立在真實資料上；B 能更早看到畫面，但之後接資料層時改動範圍較大。

## Q3. 新增卡片與「改為引言」的介面位置（SPEC 5.3 層級）

- **目前實作：** 標題詳情面板的「下層內容」區提供「＋ 段落」「＋ 下層標題」；已有段落時改為「＋ 下層標題（把現有段落移入）」。段落詳情面板底部提供「改為引言」（所屬標題還沒有引言時）。
- **問題：** 這些操作的位置與文字是否符合你的預期？設計稿沒有畫到。
